# SDF 智能应用工厂原型：实施计划（v5）

按第 13 节分 6 批开发。本次确认后做 **批次 1**，内部分 1A / 1B / 1C 三阶段，每阶段自测通过才进入下一阶段，不做只有页面没有实现的功能。

## 一、技术调整与分层

本项目固定框架为 TanStack Start（部署在 Cloudflare Workers），不使用 React Router 和 Edge Functions。服务端分三层，迁移时**复用业务核心和 Hono 路由，只替换运行环境适配层**：

```text
src/core/        纯业务逻辑（engine、blocks、llm、gates、connectors、crypto、redact）
                 只依赖接口（Db、SecretStore、Logger、Storage、Scheduler、Clock），不 import 任何运行时/Supabase
src/api/         Hono 应用：路由、trace/错误/鉴权中间件、Zod 校验；通过 ctx 注入的适配器调用 core
src/adapters/    运行环境适配：supabase-db、supabase-storage、log-writer、env、scheduler（Cloudflare/TanStack 专用）
src/routes/api/$.ts                 TanStack 入口：把 Request 交给 Hono app.fetch
src/routes/api/public/hooks/$.ts    Webhook / CI 上传 / 定时回调入口：同一 Hono 应用，经过 trace、统一错误、请求体大小限制、超时、脱敏日志、限流中间件，只跳过用户登录校验；应用身份只从上传令牌或连接器配置反查，不信任请求体
src/data/        前端数据访问层（含 realtime.ts、files.ts），组件只调这里
```

本地部署时：`core/`、`api/` 原样使用；新写 Node 入口 + 基于 `pg` 的 `adapters/`。

## 二、数据库访问适配与 Token 传递

- 前端 `src/data/http.ts` 每次请求从登录会话取 access token，放入 `Authorization: Bearer`，并带 `X-Trace-Id`。组件不接触 token。
- Hono 鉴权中间件：校验 token（`auth.getUser`），把 `userId` 写入 ctx，并创建**以该用户 token 身份访问数据库的客户端** `ctx.db`（RLS 生效）。所有业务查询只用 `ctx.db`。
- `ctx.sys`（服务端权限）只在以下系统操作中可用，且通过独立的适配器方法暴露，不暴露通用查询：密钥读写解密、`app_logs`/`client_errors` 写入、Webhook/CI 上传/定时回调、首位管理员初始化。代码审查规则写入 AGENTS.md。
- 适配接口 `Db` 以“按表/按操作的仓储函数”形式定义，迁移时用 `pg` + `SET LOCAL request.jwt.claims` 或应用层权限实现。

## 三、定时任务

- Lovable Cloud 支持 pg_cron 和 pg_net；1C 第一步先在数据库中实际查询扩展可用性，确认后再依赖。Lovable 托管环境不提供 Cloudflare Cron Trigger 配置，因此首选 **pg_cron + pg_net 定时 POST `/api/public/hooks/cron`**；若查询结果不可用，改为外部调度器调用同一接口，业务代码不变。
- 抽象 `Scheduler` 适配层：`core` 只注册任务名（`step_timeout_check`、`log_cleanup` 等），入口只负责“收到调用 → 执行任务”。本地换系统定时器调用同一接口。
- **pg_cron 端取得密钥**：`SDF_CRON_SECRET` 存入 Supabase Vault（`vault.create_secret`，由我通过一次性管理操作写入，**不写进迁移 SQL 或普通表**）。定时函数 `sdf_cron_tick()`（security definer、`SET search_path = ''`，对象全部写完整 schema 如 `vault.decrypted_secrets`、`extensions.hmac`、`net.http_post`；撤销 PUBLIC/anon/authenticated 执行权限）运行时从 `vault.decrypted_secrets` 读取，用 pgcrypto `hmac()` 计算签名，经 pg_net 发出。同一值也作为服务端环境变量供接口校验。1C 先查询 vault、pgcrypto、pg_cron、pg_net 是否都可用；任一不可用则改用外部调度器（密钥只在调度器和服务端环境变量中），并在自检页标明。
- Cron 接口安全：请求头 `X-SDF-Timestamp`（Unix 秒，整数）、`X-SDF-Nonce`（16 字节随机，小写十六进制）、`X-SDF-Signature = hex_lower(HMAC-SHA256(secret, timestamp + "
" + nonce + "
" + hex_lower(SHA256(原始请求体字节))))`；服务端在解析前读取原始字节计算；时间偏差超过 300 秒拒绝；nonce 写入 `cron_nonces(nonce primary key, seen_at)`，冲突即判为重放；常量时间比较。
- 处理顺序固定：**大小检查 → 时间戳检查 → 签名校验 → nonce 写入（防重放）→ 执行任务**；任一步失败立即返回，不进入下一步。
- nonce 清理：每次 cron 调用顺带删除 `seen_at < now() - interval '15 minutes'` 的记录（窗口大于时间容差），另有 pg_cron 每小时清理兜底。

## 四、首位管理员初始化

**所有 security definer 函数**（含 `is_admin()`、`has_app_role()`）统一 `SET search_path = ''`，引用对象写完整 schema。迁移中执行 `REVOKE CREATE ON SCHEMA public FROM PUBLIC, anon, authenticated` 并在自检页查询确认。


- 不使用“注册触发器自动设管理员”。新增表 `system_state(singleton boolean primary key default true CHECK (singleton = true), bootstrapped_at, bootstrapped_by)`，开启 RLS、不设任何策略。
- 数据库函数 `bootstrap_admin(_user_id)`（security definer，`SET search_path = ''`，表名写成 `public.system_state`、`public.user_roles`；`REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`，只授予 service_role，仅服务端调用）在一个事务中：`INSERT INTO system_state ... ON CONFLICT DO NOTHING RETURNING`，只有插入成功才写入 `user_roles(admin)`；并发时只有一个能成功。
- 入口 `POST /api/bootstrap`：要求已登录；`_user_id` 只取自服务端验证后的 Token，不接受请求参数；初始化口令放请求头 `X-SDF-Bootstrap-Token`，与 `SDF_BOOTSTRAP_TOKEN` 常量时间比较，且该请求头不写入日志。已初始化则返回 `410` 并提示入口已关闭；界面在未初始化时显示“初始化管理员”页面。
- 初始化写入审计日志。

## 五、演示人员

- `profiles` 只对应真实登录用户（外键 `auth.users`）。
- `contacts`（业务联系人/演示人员，全局）：`id, name, title, org, email?, is_demo, linked_profile_id? → profiles`。不伪造任何认证账号。contacts 的 RLS：仅当 `exists(app_contacts ac where ac.contact_id = contacts.id and has_app_role(ac.app_id, ...))` 或管理员时可见，防止跨应用泄露。
- `app_contacts`：`id uuid 主键, app_id → apps ON DELETE CASCADE, contact_id → contacts ON DELETE CASCADE, app_role, is_business`，唯一约束 `(app_id, contact_id)`，保存联系人在应用中的角色；真实账号的权限仍只看 `app_members`。
- 所有“人”的引用（需求出处、决策参与人、反馈提出人、确认人等）统一用两列：`*_profile_id → profiles`、`*_contact_id → contacts`，加约束 `CHECK (num_nonnulls(x_profile_id, x_contact_id) <= 1)`（必填字段用 `= 1`）。真实用户注册后可把 contact 关联到自己，界面优先显示真实账号。

## 六、实时刷新

- `src/data/realtime.ts` 封装订阅/退订；`useLiveRun(runId)` 等 Hook 组合“实时订阅 + 定时查询（默认 5 秒，订阅失败或断开时自动启用）”。组件不直接调用 Supabase。可通过配置只用定时查询。（实时订阅本身在批次 2 使用，批次 1 先建封装和测试。）

## 七、密钥加密（AES-GCM）

- `SDF_SECRET_KEY`：32 字节随机值的 base64 编码；启动/调用时校验长度，不合格则自检失败并拒绝加解密。
- 先生成 `secret_id`（uuid）再加密；每次加密生成 12 字节随机 IV（`crypto.getRandomValues`）；AAD 固定为 `sdf-secret:v1:<secret_id>:<kind>`，防止密文挪用。
- 存储格式：`v1:<key_id>:<base64 iv>:<base64 ciphertext+tag>`，同时存 `last4`、`updated_at`。`key_id` 为 SHA-256(密钥字节) 小写十六进制前 16 位，便于识别用错密钥。
- 重新配置：覆盖写入新密文（新 IV），记审计日志；前端只能看到后 4 位。
- 密钥丢失或更换：解密失败时返回错误编号“密钥无法解密，请重新填写”，自检页列出无法解密的条目，管理员逐条重新录入；不提供恢复。
- 脱敏：统一 `redact()` 使用**精确规则**：按字段名精确匹配（不区分大小写）`authorization, cookie, set-cookie, apikey, api_key, x-api-key, access_token, refresh_token, password, secret, client_secret, private_key, x-sdf-bootstrap-token, x-sdf-signature, x-hub-signature-256, x-gitlab-token`；按值匹配 JWT（三段 base64url）、`Bearer \S+`、`sk-[A-Za-z0-9]{16,}`、密文格式（严格匹配 `^v1:[0-9a-f]{16}:[A-Za-z0-9+/]{16}:[A-Za-z0-9+/]+={0,2}$`）；不对 `token_count`、`key_id` 等普通字段误杀。规则有单元测试。

## 八、批次 1 阶段划分

### 1A 基础权限
- 启用 Lovable Cloud、邮箱密码登录；`profiles`、`user_roles`（全局角色）、`app_members`（应用角色）、`is_admin()`、`has_app_role(app_id, roles[])`；本阶段创建的所有业务表开启行级安全并配齐授权。
- `audit_logs` 表 + 服务端审计写入方法（经系统权限写入，用户只读自己相关/管理员全读）；管理员初始化、应用新建/修改、成员增删改都写审计。
- 首位管理员初始化（第四节）；`contacts`、`app_contacts`、联系人与真实账号关联（成员页操作）。
- 工作台布局与导航、业务门户布局、「切换到业务方视角」；应用新建/编辑/成员管理；分层骨架 + Hono 入口 + 鉴权与 trace 中间件。
- **验收**：并发调用初始化只产生一个管理员，初始化后入口返回 410；非成员查不到应用（用两个账号实测）；业务方视角只见门户；审计日志中有初始化、应用和成员修改记录；用户 A 看不到仅属于应用 B 的联系人。
- **1A 完成后交付报告**：实际建表清单、RLS 策略清单、Hono 路由清单、`/api/meta` 实际输出、自测结果。

### 1B 模型与服务端
- 密钥加密（第七节）；管理 → 模型：添加、测试连接、三档任务、备用顺序、敏感数据标记。
- 模型入口按 **LiteLLM Gateway 的 OpenAI 兼容接口**设计（`base_url` + `/chat/completions`），模型 ID、地址全部从数据库读取；也兼容直接接 vLLM/Ollama。
- 模型调用层：选择、密级检查、脱敏、用量统计、执行记录；不用 Lovable AI。
- 统一错误格式与错误编号。
- **验收**：真实模型测试成功（需您提供地址和 Key）；填错地址显示中文错误和编号；数据库中只有密文，日志中无明文；敏感应用无可用模型时拒绝调用。

### 1C 诊断与种子数据
- 日志写入：`log.ts` 写入失败时只回退到 `console.error` 一次，并带“日志写入失败”标记，**绝不再次调用日志写入**（防递归）；写入有超时，不阻塞业务请求。`client_errors` 只接受已登录用户提交（经 `/api` 鉴权），登录前不开放匿名写入；登录页的错误只保存在浏览器内存，登录后再补报。
- `app_logs`、`client_errors`、前端错误收集与操作轨迹、页面级出错提示、系统日志页、诊断包导出、调试模式、日志定时清理（第三节方案）。
- `/api/meta`、系统日志、自检 `/admin/health`、诊断包**仅管理员可访问**（服务端校验）；“制造渲染错误”按钮只放在自检页。
- 种子数据**只加入批次 1 功能需要的部分**：积木、智能体角色、两个示例应用的基本信息、联系人及其应用角色、用于制品查看组件演示的少量制品（标「示例数据」）。需求、运行、反馈、验收等数据随对应批次加入。
- 制品查看组件。
- `/api/meta` 按功能列出状态：`implemented` / `schema_only` / `not_started`；提前建了表但未实现的功能标 `schema_only`，自检页显示「尚未实施」，不计为通过。
- **验收**：按错误编号查到接口日志和模型调用记录；诊断包不含密钥和认证信息（自动扫描校验）；渲染错误不白屏并写入 `client_errors`；非管理员访问上述接口返回 403；cron 签名错误、过期、重放均被拒绝；自检中本批及以前的检查项全部通过，后续功能显示「尚未实施」。
